# to-plan

## 定位

`to-plan` 只负责把需求整理成一份便于业务和研发共同评审的计划文档。它不是详细模块设计，不是任务拆解表，也不是逐步实现脚本。

计划应回答：

- 这次需求要解决什么业务问题。
- 用户、页面、接口或流程会发生什么变化。
- 核心业务逻辑如何判断、流转和兜底。
- 哪些点可以作为验收依据。
- 哪些需求点仍需和用户对齐。

## 手动触发规则

只有用户明确点名此 skill 时才使用，例如：

- `$to-plan`
- `to-plan`
- `使用 to-plan`
- `调用 to-plan`
- `用 to-plan 帮我整理`

不要因为以下请求自动使用：

- `帮我写个计划`
- `先出个方案`
- `制定开发计划`
- `拆一下任务`
- `改代码前先规划`

这些泛化请求可能需要普通回答或其他 skill，但不能自动等同于 `to-plan`。

## 工作区确认规则

在使用本技能正文能力前，必须先确认当前工作区。最终产物必须落在某个工作区内，不允许不使用工作区。

确认方式：

1. 如果用户在 prompt 中明确指定 `./doc/[工作区]/` 或工作区名称，直接使用该工作区。
2. 如果用户没有指定，根据当前 prompt 在调用方工作目录的 `./doc/` 下寻找相关工作区；找到候选后让用户确认。
3. 如果没有找到可信候选，或用户确认不复用已有工作区，就根据当前需求新建一个工作区。

工作区规则：

- 工作区路径固定为调用方工作目录下的 `./doc/[当前工作区]/`。
- 如果用户选择“寻找相关工作区”，先检查 `./doc/` 下已有子目录，优先根据需求关键词、功能名、ticket 名、已有 `plan.md` / `design.md` 内容判断候选工作区；找到候选后让用户确认具体使用哪一个。
- 新建工作区时，根据需求、功能名、ticket 名或用户给出的标题生成简洁目录名。目录名优先使用小写 kebab-case；只有中文功能名且无稳定英文标识时，可以使用简洁中文目录名。
- 工作区只负责组织 `to-plan -> to-design -> to-task` 这类连续产物，不改变 `to-plan` 重业务、轻技术的文档定位。

确认使用工作区后：

- 最终计划固定保存为 `./doc/[当前工作区]/plan.md`。
- 如果该工作区已存在 `plan.md`，先读取它，判断本次是覆盖、修订还是基于既有计划补充；如果会覆盖已有内容，先和用户确认。
- `to-plan` 是当前流程的起点，没有必须读取的前置流程文件；但已有工作区中的上下文文件可以作为理解需求的补充输入。

## 工作流

### 1. 读取需求和必要上下文

先根据用户给出的 PRD、描述、代码路径、截图、现有 TODO 或上下文理解需求。需要代码仓库事实支撑时，读取相关文件后再写，不要虚构路径、接口或业务规则。

收集重点是业务流和业务规则，而不是实现细节：

- 入口、角色、页面、状态、前置条件。
- 主流程、分支流程、异常流程。
- 数据来源、判断条件、展示规则、跳转或副作用。
- 明确包含 / 不包含的范围。
- 可以验收的观察点。

### 2. 使用 grill-me 对齐疑问

每一轮产出最终文档前，都要先用 `grill-me` 的方式检查是否存在需要对齐的问题。

执行规则：

- 如果问题可以通过读取代码、需求文档或已有上下文解决，先自行查证，不要把可查问题抛给用户。
- 如果仍存在任何会影响文档完整性的疑问，不区分阻塞和非阻塞，都按 `grill-me` 原则一次只问一个问题，并给出推荐答案。
- 用户回答后，继续检查下一处不确定点；直到所有疑问都已经对齐。
- 最终文档不能保留未对齐疑问；“已对齐的复核点”只能记录已经对齐但需要后续业务确认或执行前复核的结论，不用于承载开放问题。

### 3. 起草计划

计划内容要“重业务、轻技术”：

- 多写业务流程、规则、状态和验收。
- 少写文件级改动、组件拆分、接口封装、测试微步骤。
- 可以出现技术点，但只作为业务逻辑落地的支撑，不展开到详细模块拆解。
- 不输出完整代码、完整测试、任务工时或分阶段执行清单，除非用户额外要求。

### 4. 输出前自 review

最终保存和展示前，必须先做内部自 review。自 review 不展示给用户，发现问题必须先修改文档。

自 review 清单：

1. **需求覆盖：**用户明确提出的需求点都进入了流程、逻辑、范围、验收点或已对齐的复核项。
2. **业务优先：**文档先讲业务结果和规则，再讲必要技术支撑；没有变成文件级实现计划。
3. **流程完整：**主流程、关键分支、异常 / 兜底路径清楚。
4. **逻辑明确：**判断条件、状态变化、数据来源、展示 / 跳转规则没有空泛描述。
5. **验收可判定：**验收点能被人工、测试或接口观察验证，不写“正常工作”这类空话。
6. **范围克制：**没有扩展到用户未要求的模块拆解、重构、性能优化或任务排期。
7. **疑问处理：**所有疑问都已通过 `grill-me` 对齐；最终文档不存在开放问题。
8. **中文格式：**除文件路径、接口名、函数名、命令、字段名等字面技术值外，标题、表头、说明文字都使用中文。

### 5. 保存最终产物

最终计划必须保存到调用方工作目录：

```text
./doc/[当前工作区]/plan.md
```

保存后，在回复中说明保存路径，并给出文档要点摘要。保存动作不替代聊天回复：用户仍应看到最终计划或足够完整的摘要。

## 输出格式

除非用户指定其他格式，最终文档使用以下结构：

````markdown
# [需求名称] 计划

## 1. 背景和目标

- **背景：**[需求出现的业务背景、问题或触发原因]
- **目标：**[本次要达成的业务结果]
- **不解决：**[明确不在本次处理的内容；没有则写“暂无明确排除项”]

## 2. 范围

| 类型 | 内容 |
| --- | --- |
| 包含 | [本次覆盖的页面、入口、角色、状态或流程] |
| 不包含 | [明确排除的内容] |
| 前提 | [依赖的业务前提、已有能力或用户已确认事项] |

## 3. 流程

### 3.1 主流程

1. [用户 / 系统从哪里进入]
2. [发生什么判断、展示或操作]
3. [最终到达什么状态或结果]

### 3.2 分支和兜底

| 场景 | 触发条件 | 处理方式 | 结果 |
| --- | --- | --- | --- |
| [场景名] | [条件] | [业务处理] | [用户或系统看到的结果] |

## 4. 逻辑描述

| 逻辑点 | 规则 | 说明 |
| --- | --- | --- |
| [判断 / 展示 / 跳转 / 数据逻辑] | [具体规则] | [必要的技术或业务补充] |

## 5. 验收点

- [ ] [可观察的主流程结果]
- [ ] [关键分支或异常场景]
- [ ] [数据、状态、文案、跳转或接口表现]
- [ ] [必要的回归检查]

## 6. 已对齐的复核点

- [已经对齐、但后续执行或业务评审时建议复核的结论；没有则写“暂无”]
````

## 写作边界

必须避免：

- 把计划写成详细模块设计文档。
- 把每个组件、函数、hook、service 都拆成独立章节。
- 输出任务列表、工时、排期或“阶段 1 / 阶段 2”式执行计划。
- 用大量代码块替代业务规则描述。
- 用 `TBD`、`TODO`、`待补充` 占位。
- 对关键流程写“按现有逻辑处理”但不说明现有逻辑是什么。

可以适度包含：

- 关键文件路径、接口名、字段名，用于说明逻辑来源。
- 简短的数据来源说明。
- 必要的技术约束或风险，但不展开成详细实现方案。

## 交付话术

完成后使用简短回复：

```markdown
已生成 `to-plan` 文档并保存到 `[保存路径]`。

核心内容：
- [流程摘要]
- [逻辑摘要]
- [验收摘要]
```

如果仍有任何问题未对齐，先按 `grill-me` 方式提问，不要生成半成品计划。
