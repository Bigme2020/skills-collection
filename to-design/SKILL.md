# 模块设计（to-design）

使用本技能将需求文档转换为详细的模块设计文档。最终产物不是分析过程、路线图、任务清单，也不是泛泛的技术方案；它应该是一份以模块为中心的设计文档，为后续实现计划提供足够具体的结构。

## 工作区确认规则

在使用本技能正文能力前，必须先确认当前工作区。最终产物必须落在某个工作区内，不允许不使用工作区。

确认方式：

1. 如果用户在 prompt 中明确指定 `./docs/[工作区]/` 或工作区名称，直接使用该工作区。
2. 如果用户没有指定，根据当前 prompt 在调用方工作目录的 `./docs/` 下寻找相关工作区；找到候选后让用户确认。
3. 如果没有找到可信候选，或用户确认不复用已有工作区，就根据当前需求新建一个工作区。

工作区规则：

- 工作区路径固定为调用方工作目录下的 `./docs/[当前工作区]/`。
- 如果用户选择“寻找相关工作区”，先检查 `./docs/` 下已有子目录，优先根据需求关键词、功能名、ticket 名、已有 `plan.md` / `design.md` 内容判断候选工作区；找到候选后让用户确认具体使用哪一个。
- 新建工作区时，根据需求、功能名、ticket 名或用户给出的标题生成简洁目录名。目录名优先使用小写 kebab-case；只有中文功能名且无稳定英文标识时，可以使用简洁中文目录名。
- 工作区只负责组织 `to-plan -> to-design -> to-task` 这类连续产物，不改变 `to-design` 模块设计文档的定位。

确认使用工作区后：

- 最终模块设计固定保存为 `./docs/[当前工作区]/design.md`。
- 如果当前工作区存在 `plan.md`，在开始模块设计前读取它，并作为背景输入之一。
- 如果当前工作区缺少 `plan.md`，不阻塞 `to-design`；可以根据用户提供的外部 plan、PRD、功能说明、代码上下文或其他需求输入生成 `design.md`。最终设计仍必须保存到当前工作区。
- 如果该工作区已存在 `design.md`，先读取它，判断本次是覆盖、修订还是基于既有设计补充；如果会覆盖已有内容，先和用户确认。

## 设计倾向

模块应高内聚、低耦合，并且能够独立测试。

每个模块都应该：

- 拥有一个清晰的技术职责。
- 暴露收敛的输入/输出契约。
- 避免读取其他模块的私有状态。
- 通过明确的 interface、adapter、DTO、event 或注入服务依赖其他模块。
- 能够在 mock 依赖的情况下测试，而不需要运行完整产品流程。
- 具备足够细节以支撑后续任务拆分，但不要把设计文档写成任务拆解文档。

如果两个模块必须理解彼此的内部实现，先重新调整边界，再撰写最终文档。

## 输入处理

接受以下形式的需求输入：本地文件路径、粘贴文本、可访问的文档链接，或和仓库相关的功能说明。如果需求和仓库有关，在命名模块、文件、API、hook、store、路由、事件或数据类型之前，先检查当前检出的代码。

只提取会影响模块设计的事实：

- 业务目标和用户可感知结果。
- 必要流程和系统行为。
- 数据实体、状态流转、权限、约束和外部依赖。
- 需求中提到的已有系统、API、页面、模块、服务或约定。
- 非目标、已确认约束和需要在产出前对齐的问题。

不要在最终文档中放很长的需求摘要。对需求的理解应该体现在模块决策里。

## 对齐规则

当不确定性会影响模块边界、归属、接口、持久化、权限、兼容性、发布策略或测试策略时，使用 `grill-me` 和用户对齐。一次只问一个问题，并说明：

- 这个问题为什么会影响设计。
- 推荐答案。
- 如果用户选择不同答案，会产生什么后果。

不要询问可以通过阅读需求或当前代码库回答的问题。最终设计文档必须是确定的：对于任何仍会影响设计完整性的问题，不区分阻塞或非阻塞，都必须先继续按 `grill-me` 提问，直到对齐后再保存 `design.md`。

最终文档规则：

- 不允许把开放问题写进最终文档。
- 不允许保留“风险与待确认”“待确认”“TBD”“TODO”“待补充”这类栏目或占位。
- 如果问题可以通过阅读需求、代码或已有上下文解决，先自行查证并写成确定结论。
- 已对齐但后续执行时需要注意的内容，只能写成“已确认约束”“已确定取舍”或模块内的确定处理策略，不能写成待确认项。

## 必需输出形态

除非用户另有要求，最终文档必须使用中文。

## 必需文件输出

始终把生成的设计文档写入调用方当前工作目录的工作区下：

```text
./docs/[当前工作区]/design.md
```

工作区模式写入文档前：

- 如果 `./docs/[当前工作区]/` 不存在，先创建它。
- 如果 `plan.md` 存在，把它作为背景输入之一读取并纳入设计依据。
- 如果 `design.md` 已存在，先读取旧文件，并在覆盖前确认。

顶级章节必须遵循以下结构：

- `1. 概述` 是唯一的全局概述章节。设计原则、模块架构、核心机制、跨模块关系、已确认约束和已确定取舍都放在这里。
- 从 `2.` 开始，每个顶级章节都必须是一个具体模块。不要在第 1 节之后创建“数据模型”“测试方案”“发布计划”“待确认事项”这类非模块顶级章节。相关内容应放进对应模块章节；只有真正跨模块的内容才放进 `1. 概述`。
- 每个模块章节都要足够详细，能够支撑后续任务拆分，但仍然必须保持模块设计章节的形态。

## 模块章节要求

从 `2.` 开始，每个模块章节都必须包含：

- 模块职责：说明它负责什么，以及明确不负责什么。
- 输入：说明来源、类型/结构、约束和示例。
- 输出：说明消费方、类型/结构、触发时机和示例。
- 依赖：说明每个依赖为什么需要、如何隔离、是否可以 mock。
- 结构：说明建议的文件、类、函数、子组件，以及最小对外契约。
- 独立测试方案：说明单测对象、mock 依赖、正常用例、边界用例和异常用例。
- 可实施性：模块设计必须足够具体，使后续任务拆分可以识别实现单元、输入、输出和验收标准，而不需要重新设计模块。

如果某个模块无法独立测试，先调整设计。如果因为外部约束导致确实无法独立测试，在该模块内说明约束，并提供最窄可行的集成测试方案。

## 跨模块指导

跨模块内容要保持紧凑，并放在 `1. 概述`。只用它说明模块如何协作：

- 模块架构表。
- 数据流和调用/事件机制。
- 共享边界规则。
- 全局已确认约束和已确定取舍。

不要把模块专属的接口、数据结构、测试或任务放进全局章节。它们属于对应的归属模块。

## 输出前自检

保存 `design.md` 前必须检查：

1. 所有影响模块边界、接口、状态、权限、兼容性、发布策略或测试策略的问题都已通过查证或 `grill-me` 对齐。
2. 最终文档没有开放问题，没有“风险与待确认”“待确认”“TBD”“TODO”“待补充”栏目或占位。
3. `1.6` 只记录已确认约束与已确定取舍，不记录需要后续再问的问题。
4. 从 `2.` 开始的每个顶级章节仍然都是具体模块，且模块内职责、输入、输出、依赖、结构和独立测试方案完整。

## 避免事项

避免：

- 文档主要由流程步骤构成。
- 先给一个全局“模块总览”，然后每个模块只有浅层描述。
- 在 `1. 概述` 之后出现不是具体模块的顶级章节。
- 没有模块契约的泛泛架构描述。
- 用一个大模块承载大部分行为。
- 通过共享全局变量、隐式状态或私有跨模块调用制造隐藏耦合。

生成的文件应该是一份详细的模块设计文档，其中 `2+` 章节都是具体模块。它应该能够支撑后续任务拆分，但除非用户明确要求，否则不要包含任务拆分表。
