# 编写计划

## 概览

创建简洁的实现计划，方便人工在改代码前快速评审。计划首先是评审文档，其次才是执行辅助；它应该让范围、用户可见行为、视觉 / 文案变化、技术方案、风险和验收标准都易于浏览。

避免把计划写成伪代码或执行流水账。只要目标、文件、约束和验证路径清楚，熟练工程师或 agent 可以自行推导常规编辑细节。

**开始时说明：**`我会使用 write-plan skill 生成一份简洁、可评审的中文实现计划。`

**默认保存到：**`docs/plans/YYYY-MM-DD-<feature-name>.md`

用户指定的计划位置优先于默认位置。

## 计划优先级

按以下顺序优化可评审性：

1. **用户结果：**用户会看到或感受到什么变化，包括界面、文案、流程、状态和行为。
2. **范围边界：**包含什么、明确不包含什么、哪些假设需要确认。
3. **技术形态：**文件、组件、接口、数据流和集成点的高层方案。
4. **验收：**评审者可用来批准或拒绝实现的具体检查项。
5. **执行：**精简阶段，而不是逐行步骤。

## 上下文收集

起草前，先检查足够的仓库上下文，避免通用空话：

- 相关文件、测试、路由、组件、脚本和约定。
- 现有命名、布局、样式、错误处理和测试风格示例。
- 框架、语言、测试运行器、格式化工具、构建命令。
- 仅当行为或语法重要时，查询外部接口 / 库的当前文档。

反映真实仓库路径和约定。不要虚构架构。

## 范围检查

如果请求跨越可以独立交付的子系统，建议拆成多个计划。不要仅因为工作有多个步骤就拆分。

## 计划长度

默认目标：1-2 页 Markdown。

使用短列表和表格。优先使用图示、状态列表和验收标准，少用代码块。

大型工作中，保持顶层计划可评审；只有必要时才把更深的实现说明放入简短附录。

## 语言规则

计划内容必须严格使用中文。不要在中文输出中混入英文标题、标签、连接词或解释性文字。

- 使用中文章节标题、字段标签、表头、清单标签和交付话术。
- 字面技术值保持原样：文件路径、命令、包名、接口名、函数 / 组件名、代码片段、环境变量和错误文本。
- 通用计划术语必须翻译：使用 `目标`，不要使用 `Goal`；使用 `范围`，不要使用 `Scope`；使用 `验收标准`，不要使用 `Acceptance Criteria`；使用 `验证`，不要使用 `Verification`；使用 `风险 / 待确认问题`，不要使用 `Risks / Open Questions`。
- 展示或保存计划前，扫描是否有误入的英文说明、英文标题或中英文混排，并改成中文。

## 代码细节规则

计划应是简化代码，而不是完整代码：

- 只有在说明接口、数据形态、路由契约或非显然算法时才包含代码。
- 代码片段控制在约 20 行以内，并标明它是草图，不是最终实现。
- 不包含完整实现、完整测试体、重复样板、导入语句或提交命令。
- 除非用户明确要求 TDD 微步骤，不要写“先写失败测试、运行、实现最小代码”这类细碎步骤。
- 已知时，写出准确文件路径和函数 / 组件名称。

## 必需计划模板

除非用户要求其他格式，否则使用此结构：

```markdown
# [功能名称] 计划

**目标：**[一句话说明]
**评审重点：**[需要人工重点确认的内容：体验、文案、数据契约、风险等]

## 用户可见结果

- [可见行为、界面状态、流程、文案或 API 结果]
- [必要时写明前后对比]

## 范围

**包含：**[本次包含的工作]
**不包含：**[明确排除的工作]
**假设：**[需要评审者同意的前提]

## 设计 / 体验说明

- [视觉层级、布局、状态、空 / 错误 / 加载态、响应式行为]
- [文案变化或措辞原则]

## 技术方案

| 领域 | 决策 | 文件 |
| --- | --- | --- |
| [界面 / API / 数据 / 测试] | [简短方案] | `path/to/file` |

## 数据 / 接口形态

[仅在有帮助时提供小型草图]

```ts
type Example = {
  id: string
  label: string
}
```

## 实施阶段

- [ ] 阶段 1：[用户可见或技术切片；最多 1-3 个要点]
- [ ] 阶段 2：[下一个切片]
- [ ] 阶段 3：[验证和清理]

## 验收标准

- [ ] [评审者可观察的行为]
- [ ] [边界状态或错误处理]
- [ ] [测试 / 构建 / lint 预期]

## 验证

- `command to run` - [证明什么]
- [界面相关的手动检查、截图或浏览器流程]

## 风险 / 待确认问题

- [风险或问题；如果影响范围，标记为阻塞]
```

## 章节指引

**用户可见结果：**这是最具体的章节。界面工作要描述可见布局、交互状态、文案和响应式行为。后端 / 接口工作要描述可观察的契约变化和失败模式。

**设计 / 体验说明：**用能帮助评审者想象结果的语言。说明视觉层级、密度、对比度、加载 / 空 / 错误状态，以及移动端 / 桌面端行为。如有设计素材，引用它们。

**技术方案：**保持在模块 / 文件职责层级。说明为什么该方案安全且最小。

**实施阶段：**每个阶段应可评审，并尽量接近可交付切片。避免 2 分钟级任务。好的阶段通常是 30-90 分钟的工作，或一个连贯切片。

**验收标准：**写成人工可验证的标准。包含重要边界情况和回归检查。

最终章节名和标签必须使用上面的中文模板，即使仓库、框架或源文档使用英文术语。

## 禁止占位

以下属于计划失败：

- `TBD`、`TODO`、`implement later`、`fill in details`。
- 写“处理边界情况”但不说明具体边界。
- 只列文件、不说明职责。
- 验收标准只写“正常工作”。
- 验证命令没有简短说明它证明什么。
- 大段代码让评审更困难，而不是更清楚。

## 输出前自审硬门禁

展示或保存计划前，必须完成一次严格的内部自审。自审不是建议、附录、后续动作或给用户选择的选项，而是计划交付前的强制质量门禁。

执行方式：

1. 起草完整计划。
2. 对照下方清单逐项判定 `通过` / `失败`。
3. 任一项失败时，必须先修改计划，再重新从第 1 项开始检查。
4. 只有全部通过后，才能保存或展示计划。

自审清单：

1. **可浏览性：**评审者能在两分钟内理解目标、用户可见结果 / 体验、范围、风险和验收标准。
2. **规格覆盖：**用户提出的每个需求都映射到范围、技术方案、验收标准或待确认问题，且没有遗漏。
3. **人工评审价值：**计划先说明视觉、文案、行为、流程或 API 可观察结果，再说明代码机制。
4. **范围边界：**包含、不包含和假设具体明确；不把未确认范围伪装成已确定事项。
5. **具体路径：**涉及文件、模块、组件、接口和职责足够具体，便于直接实现；未知路径明确标为待确认。
6. **避免过度细节：**移除不影响评审的样板代码、逐行编辑步骤、微任务、重复命令和完整测试体。
7. **验证可执行：**验证命令和手动检查都说明证明什么；没有空泛的“测试通过”“正常工作”。
8. **中文格式：**除字面技术值外，标题、标签、表头、列表、交付话术和解释性文字全为中文。
9. **无占位失败项：**不存在 `TBD`、`TODO`、`implement later`、`fill in details`，也不存在“处理边界情况”但未说明具体边界。

交付限制：

- 不输出未修订初稿。
- 不输出自审过程、逐项打分或“我已自审”的空泛声明。
- 不把自审发现留给用户处理。
- 最终只交付通过门禁后的计划和后续执行选择。

## 内部评审

对较大的计划，如果可用 subagent / task 工具，使用 `plan-document-reviewer-prompt.md` 作为内部评审提示词。完整计划起草完成后、最终输出前派发评审，并把发现用于修订计划。

按以下方式处理评审发现：

- 阻塞问题：展示计划前必须修复。
- 建议改进：只有在能提升清晰度、可评审性或执行安全性时才采纳。
- 纯风格建议：除非用户要求该风格，否则忽略。

无论是否调用 subagent，都必须至少自行完成上面的输出前自审。

## 执行交接

保存完成内部自审并修订后的计划后，提供执行选项，但不要假设特定执行框架：

```markdown
计划已完成并保存到 `docs/plans/<filename>.md`。

执行选项：

1. 按阶段实现 - 执行一个阶段、验证，然后暂停等待确认。
2. 仅保留计划 - 计划交给其他工程师或 agent 后续执行。

选择哪种方式？
```

如果用户选择执行，按阶段执行计划。遇到失败或范围不明确时停止并诊断，再继续。
