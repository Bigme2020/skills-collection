# to-code

> [!WARNING]
> **Deprecated / 已废弃（提示性）**：新工作流请使用 `implement`，由它读取既有 tickets、按依赖调度 sub-agent、完成 review/修复/本地 commit，并禁止 push。本 skill 仅用于迁移期回退；用户显式调用时仍按下述原契约执行。

## 定位

`to-code` 是 `to-plan -> to-design -> to-task` 之后的自动实现环节。它负责读取当前工作区的设计和任务文档，把 `tasks/` 下的模块任务转成真实代码、测试和进度更新。

本技能不是重新写需求、不是重新做模块设计、也不是重新拆任务。它只执行已经由 `to-task` 产出的任务，并在必要时把执行发现的问题反馈到任务进度中。

## 手动触发规则

只有用户明确点名此 skill 或明确要求基于 `tasks/progress.md` 自动实现代码时才使用，例如：

- `$to-code`
- `to-code`
- `使用 to-code`
- `调用 to-code`
- `用 to-code 实现任务`
- `根据 docs/<工作区>/tasks 自动把代码写完`

不要因为用户泛泛说“实现一下”“继续开发”“把任务做掉”就自动使用；这些请求可能需要普通编码流程或其他 skill。

## sub-agent 前置条件

`to-code` 的执行模型依赖真实 sub-agent。用户明确触发 `to-code` 时，视为允许主 Agent 使用当前运行环境提供的 sub-agent / multi-agent 工具，例如 Codex CLI 中的 subagent 能力。

执行规则：

- 主 Agent 必须在实现前确认当前环境存在可用的 sub-agent 工具或等价多 Agent 调度能力。
- 每个模块级执行者都必须是真实子 Agent，不把“子 Agent”降级成主 Agent 的普通串行自我模拟。
- 如果当前环境没有 sub-agent 能力、工具被禁用，或用户没有授权使用 sub-agent，停止执行代码实现，说明缺少的能力，并提示启用 sub-agent 后重新触发 `to-code`。

## 工作区确认规则

在使用本技能正文能力前，必须先确认当前工作区。最终实现必须基于某个工作区的文档链路，不允许脱离工作区执行。

确认方式：

1. 如果用户在 prompt 中明确指定 `./docs/[工作区]/` 或工作区名称，直接使用该工作区。
2. 如果用户没有指定，根据当前 prompt 在调用方工作目录的 `./docs/` 下寻找相关工作区；找到候选后让用户确认。
3. 如果没有找到可信候选，先告知缺少可执行工作区，并建议先完成 `to-plan -> to-design -> to-task`。

确认工作区后，必须读取：

- `./docs/[当前工作区]/design.md`
- `./docs/[当前工作区]/tasks/progress.md`
- `./docs/[当前工作区]/tasks/` 下除 `progress.md` 外递归查找的所有任务文件

如果存在，则同时读取：

- `./docs/[当前工作区]/plan.md`

缺失处理：

- 缺少 `design.md`：停止实现，建议先执行 `to-design`。
- 缺少 `tasks/progress.md` 或模块任务文件：停止实现，建议先执行 `to-task`。
- 缺少 `plan.md`：不阻塞；只把 `design.md` 和 tasks 作为主输入。

## 输入优先级

实现时按以下优先级理解需求：

1. `tasks/` 模块任务文件：决定当前要做什么、完成标准和验证方式。
2. `tasks/progress.md`：决定整体模块顺序、已完成状态和依赖关系。
3. `design.md`：决定模块边界、输入输出契约、依赖隔离、核心逻辑和独立测试要求。
4. `plan.md`：仅作为业务目标、流程和验收背景。
5. 当前代码库：决定真实文件位置、既有模式、测试框架、命名、架构和可复用能力。

如果任务文件与 `design.md` 冲突，默认以 `design.md` 的模块契约为准，并把冲突记录到最终回复；只有用户明确要求修订任务时才改写任务目标。

## 主 Agent 职责

主 Agent 负责整体调度，不直接长时间陷入某个模块实现。

主 Agent 必须完成：

1. 读取工作区输入文件，建立模块清单。
2. 确认当前环境具备并允许使用 sub-agent / multi-agent 能力。
3. 读取当前代码库，确认项目技术栈、测试命令、代码风格和可能的修改位置。
4. 根据 `progress.md` 和任务文件识别未完成任务、架构归属、业务归属、依赖图和可并行任务。
5. 为每个边界独立的可执行任务生成一个真实子 Agent 任务。
6. 控制子 Agent 的写入边界，尽量让不同子 Agent 修改互不重叠的文件。
7. 汇总子 Agent 的结果，检查代码、测试、进度文档是否一致。
8. 更新 `tasks/progress.md` 和对应模块任务文件中的 checklist 状态。
9. 执行必要的最终验证命令。
10. 给出最终实现摘要、测试结果、未完成项和风险。

主 Agent 不应把整个仓库上下文原样塞给子 Agent。它应该给子 Agent 提供足够具体、边界清楚的任务说明。

## 子 Agent 职责

每个子 Agent 只负责一个具有明确架构归属和业务归属的任务单元，或同一双重归属下可独立实现的一组子任务。

子 Agent 必须完成：

1. 读取主 Agent 指定的模块任务文件和相关 `design.md` 章节。
2. 在当前代码库中定位最小修改面。
3. 按模块任务 checklist 实现功能。
4. 补齐或更新测试用例，覆盖任务文件中的验证方式和 `design.md` 的独立测试方案。
5. 运行与本模块相关的最小验证命令。
6. 在最终输出中列出修改文件、完成的 checklist、测试命令和结果、剩余风险。

子 Agent 不应该：

- 修改其他模块的任务目标。
- 重写 `plan.md`、`design.md` 或无关任务文件。
- 做和模块任务无关的重构。
- 越过任务的架构归属实现其他端、层、进程或部署单元的职责。
- 跳过测试用例，除非当前仓库没有可运行测试框架；这种情况必须说明原因并给出替代验证。

## 子 Agent 任务模板

主 Agent 生成子 Agent 时，使用以下模板：

````markdown
你是 `to-code` 的模块实现子 Agent。只处理下面这个模块，不要扩展范围。

## 工作区

- 工作区路径：`./docs/[当前工作区]/`
- 计划文档：`./docs/[当前工作区]/plan.md`（如存在）
- 设计文档：`./docs/[当前工作区]/design.md`
- 总体进度：`./docs/[当前工作区]/tasks/progress.md`
- 当前任务：`./docs/[当前工作区]/tasks/[task-path].md`

## 当前任务

- 任务名称：[任务名]
- 架构归属：[任务文件中的架构单元]
- 业务归属：[任务文件中的业务能力]
- 设计章节：[design.md 中对应章节]
- 前置依赖：[依赖图中已完成的任务]
- 本次允许修改范围：[主 Agent 根据代码库判断出的文件/目录；如无法提前判断，写“先定位后保持最小修改面”]
- 禁止修改范围：[其他架构单元拥有的文件/目录或状态]

## 必做事项

1. 读取当前模块任务文件和对应设计章节。
2. 定位真实代码入口、依赖和测试位置。
3. 逐项完成未勾选子任务。
4. 为本模块补齐或更新测试用例。
5. 运行最小相关验证命令。
6. 不要修改无关模块，不要重写前置文档。

## 输出要求

最终回复必须包含：

- 已修改文件列表。
- 已完成的任务 checklist。
- 新增或更新的测试用例摘要。
- 实际运行的验证命令和结果。
- 如果未能完成，说明具体阻塞点、已尝试的查证路径和建议的下一步。
````

## 调度流程

### 1. 建立执行视图

主 Agent 读取所有输入后，先整理：

- 模块列表：来自 `progress.md` 和模块任务文件。
- 双重归属：每个任务对应的架构单元和业务能力。
- 模块状态：未开始、进行中、已完成、无法执行。
- 依赖图：来自 `progress.md` 和任务文件，依据接口生产消费、数据所有权、运行前置条件和写入冲突建立。
- 验证矩阵：每个模块应该运行哪些单测、集成测试、类型检查、lint 或人工检查。

如果 `progress.md` 和模块文件状态不一致，以模块文件内子任务状态为准，并在更新 `progress.md` 时修正整体状态。

### 2. 处理疑问

执行前先检查是否存在会影响代码正确性的疑问。

处理规则：

- 可以通过读取 `plan.md`、`design.md`、tasks 或当前代码库解决的问题，先自行查证。
- 可以通过现有文档和代码形成保守确定处理策略的问题，按该策略推进，并在最终回复中说明依据；不能把影响接口契约、数据归属或用户可见行为的问题作为开放假设带进实现。
- 如果疑问会影响接口契约、数据归属、用户可见行为、兼容策略或测试判断，且无法从文档和代码中解决，使用 `grill-me` 一次只问一个问题，并给出推荐答案。
- 一旦进入子 Agent 执行阶段，默认整个过程不再等待人工参与；阻塞疑问必须在生成子 Agent 前尽量消解。

### 3. 生成子 Agent

主 Agent 根据 design 和 tasks 中的依赖图分批生成子 Agent：

- 无依赖或依赖已完成的模块可以并行。
- 共享同一核心文件、同一接口契约或同一测试夹具的模块不要并行写入；按依赖顺序串行。
- 不预设页面端、服务端、基础设施或任何固定架构单元的执行先后；顺序只能来自已记录依赖。
- 每个子 Agent 的任务必须有清楚的架构归属、业务归属、修改边界、输入文件、完成标准和验证要求。
- 如果环境没有可用的子 Agent 工具，主 Agent 停止执行，不在当前会话中串行模拟子 Agent。

### 4. 集成结果

每个子 Agent 完成后，主 Agent 必须：

- 阅读子 Agent 的修改摘要和验证结果。
- 检查是否越界修改。
- 对照模块任务 checklist 判断是否真的完成。
- 必要时补充小范围修正，但不要替子 Agent 做大范围返工。
- 将完成状态写回模块任务文件。

如果子 Agent 失败，主 Agent 先判断是否能自行修复；无法修复时，把模块标记为未完成并记录阻塞原因，不要虚假勾选。

### 5. 更新进度

模块任务文件更新规则：

- 完成的子任务从 `[ ]` 改成 `[x]`。
- 完成的模块验收从 `[ ]` 改成 `[x]`。
- 未完成项保持 `[ ]`，并在“备注”或新增“执行记录”中写明原因。

`progress.md` 更新规则：

- 只有当某模块任务文件中的所有子任务和模块验收都完成时，才把该模块进度改成 `[x]`。
- 全体验收只有在所有模块完成且最终验证通过后才勾选。
- 保留原有模块链接和依赖顺序，不随意重排；如果执行发现依赖顺序错误，可以追加说明。

建议在每个模块任务文件末尾追加：

````markdown
## 执行记录

- [YYYY-MM-DD] to-code：完成 [任务摘要]；验证：[命令和结果]；备注：[无/风险说明]
````

## 测试策略

每个模块都必须优先补齐自动化测试。

测试选择顺序：

1. 先找离修改点最近的现有测试，沿用同一测试框架和 mock 风格。
2. 如果没有现有测试，为模块新增最小可维护测试。
3. 如果当前项目没有测试基础设施，使用类型检查、lint、构建、脚本运行或手工可观察步骤作为替代验证，并说明测试缺口。

测试内容必须覆盖：

- 任务文件中写明的验证方式。
- `design.md` 中对应模块的正常、边界和异常用例。
- 本次实现新增或改变的外部可见行为。

## 代码实现边界

实现时遵循当前代码库约定：

- 优先复用已有模块、helper、service、hook、组件、测试工具和类型。
- 保持最小修改面，不做无关重构。
- 不引入新依赖，除非任务或设计明确要求；必须引入时先说明原因。
- 不改变公共契约，除非 `design.md` 或任务文件明确要求。
- 不跨越任务声明的架构归属修改其他端、层、进程或部署单元；跨归属修改必须由独立契约/集成任务授权。
- 不删除用户已有改动；遇到脏工作区时只处理本任务相关文件。

## 输出前自检

完成前主 Agent 必须检查：

1. 已确认当前工作区。
2. 已确认当前环境具备并允许使用真实 sub-agent / multi-agent 能力。
3. 已读取 `design.md`、`tasks/progress.md` 和所有模块任务文件；如存在 `plan.md` 也已读取。
4. 每个已执行模块都有对应真实子 Agent 输出。
5. 已完成任务的 checklist 与真实代码和测试结果一致。
6. `progress.md` 没有把未完全完成的模块误标为完成。
7. 自动化测试已尽量补齐；无法补齐时说明原因和替代验证。
8. 最终验证命令已运行，或明确说明无法运行的原因。
9. 没有留下未说明的开放问题；如存在阻塞疑问，已按 `grill-me` 对齐或标记为未完成。
10. 每个子 Agent 的修改范围符合任务的架构归属和业务归属，没有按固定前后端顺序替代真实依赖图。

## 交付话术

完成后使用简短回复：

```markdown
已执行 `to-code`，基于 `./docs/[当前工作区]/tasks/` 完成代码实现。

核心结果：
- 已完成模块：[模块列表]
- 未完成模块：[模块列表；没有则写“无”]
- 进度文件：`./docs/[当前工作区]/tasks/progress.md`
- 主要修改：[文件或目录摘要]
- 验证：[命令和结果]
```

如果因为缺少 `design.md`、缺少 tasks、测试环境不可用或阻塞疑问而无法完成，直接说明当前停在哪一步、已经查证过什么、下一步需要什么。
