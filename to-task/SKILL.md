# to-task

## 定位

`to-task` 负责把已经确认的计划和模块设计拆成最小可执行任务，供后续 vibe coding 逐项完成。它不是重新写需求、不是重新做模块设计，也不是排期或工时评估。

任务应回答：

- 每个模块要完成哪些最小实现单元。
- 每个任务的输入、输出、完成标准是什么。
- 子任务之间是否存在顺序依赖。
- 当前模块和整体模块是否完成。

## 手动触发规则

只有用户明确点名此 skill 或明确要求把模块设计拆成 vibe coding 任务时才使用，例如：

- `$to-task`
- `to-task`
- `使用 to-task`
- `调用 to-task`
- `用 to-task 拆任务`
- `根据 design 生成 vibe coding 任务`

不要因为用户泛泛说“下一步怎么做”“实现一下”“列个 TODO”就自动使用；这些请求可能需要普通实现或其他 skill。

## 工作区确认规则

在使用本技能正文能力前，必须先确认当前工作区。最终产物必须落在某个工作区内，不允许不使用工作区。

确认方式：

1. 如果用户在 prompt 中明确指定 `./docs/[工作区]/` 或工作区名称，直接使用该工作区。
2. 如果用户没有指定，根据当前 prompt 在调用方工作目录的 `./docs/` 下寻找相关工作区；找到候选后让用户确认。
3. 如果没有找到可信候选，或用户确认不复用已有工作区，停止生成任务，并提示用户先通过 `to-design` 建立包含 `design.md` 的工作区。

工作区规则：

- 工作区路径固定为调用方工作目录下的 `./docs/[当前工作区]/`。
- 如果用户没有指定工作区，先检查 `./docs/` 下已有子目录，优先根据需求关键词、功能名、ticket 名、已有 `plan.md` / `design.md` 内容判断候选工作区；找到候选后让用户确认具体使用哪一个。
- `to-task` 不创建新工作区；它只能在已有工作区的 `design.md` 基础上生成 `tasks/`。
- 工作区只负责组织 `to-plan -> to-design -> to-task` 这类连续产物，不改变 `to-task` 最小可执行任务拆分的定位。

确认工作区后：

- 必须读取 `./docs/[当前工作区]/design.md`。
- 如果 `./docs/[当前工作区]/plan.md` 存在，将它作为背景解释补充读取。
- 如果缺少 `design.md`，先告知用户缺少设计文件，并建议先补齐 `to-design`；不要凭空生成任务。
- 如果缺少 `plan.md`，不阻塞 `to-task`，直接基于 `design.md` 拆分任务。
- 如果 `./docs/[当前工作区]/tasks/` 已存在，先读取已有 `progress.md` 和模块任务文件，判断本次是覆盖、修订还是补充；如果会覆盖已有勾选状态，先和用户确认。

## 输入处理

以当前工作区的 `design.md` 为主输入，`plan.md` 只作为可选背景输入：

- `design.md` 用于识别模块、模块职责、输入、输出、依赖、结构、核心逻辑、异常降级和独立测试方案。
- 同时读取 `design.md` 中的架构轴、业务轴、映射矩阵、依赖方向和一维退化说明；`to-task` 只能消费这些结论，不能自行重新设计架构。
- 如果存在 `plan.md`，用它补充理解业务目标、范围、流程、逻辑和验收点。
- 如果不存在 `plan.md`，不要要求补齐；从 `design.md` 中提取足够的业务背景和验收依据。

如果用户额外提供代码路径、截图、PRD 或补充说明，可以作为辅助输入；但不能覆盖 `design.md` 中已经明确的约束，除非用户明确要求更新前置文档。

## 拆分原则

每个模块都要拆成适合 vibe coding 的最小任务。

每个任务应该：

- 只对应一个可执行动作或一个很小的实现单元。
- 有清晰的完成标准，可以通过代码、测试、文档或人工检查判断。
- 尽量避免跨模块修改；必须跨模块时说明依赖和原因。
- 能让后续实现者按 checklist 顺序推进，而不需要重新理解完整需求。
- 不写工时、排期、负责人，也不生成阶段式项目计划。

当 design 存在二维拆分时：

- 每个任务必须有唯一主要架构归属和明确业务归属；禁止把多个架构单元的实现塞进同一个任务。
- 任务目录的第一层来自 design 中的架构轴，第二层按业务能力或可独立交付单元组织；不写死 `client/server/admin` 等名称。
- 一个 design 模块跨越多个架构单元时，按映射矩阵拆成多个任务文件，并通过明确契约或集成任务连接；不要为了维持“一模块一文件”重新混合架构边界。
- 跨架构单元共享的接口、DTO、事件或 schema 必须标明唯一生产者和消费者。只有确实需要独立交付时才拆成契约任务，不能机械增加空壳任务。
- 依赖关系由接口生产消费、数据/状态所有权、运行前置条件和实际写入冲突推导，不预设基础设施、服务端或页面端的固定先后顺序。

当 design 明确退化为一维时，沿用原有“一模块一任务文件”结构，不创建空的架构目录。

不要把任务写成空泛动作，例如“完善逻辑”“处理异常”“补充测试”。要写清楚完善什么逻辑、哪些异常、测试覆盖什么输入和结果。

## 输出文件

最终产物必须写入：

```text
./docs/[当前工作区]/tasks/<task-path>.md
./docs/[当前工作区]/tasks/progress.md
```

写入规则：

- 如果 `./docs/[当前工作区]/tasks/` 不存在，先创建它。
- 每个 `design.md` 中具体模块的实现职责都必须被任务文件完整覆盖；一维设计通常对应一个模块文件，二维设计允许按架构归属拆成多个任务文件。
- `<task-path>` 从 design 的架构轴与业务轴映射推导；二维设计优先使用 `<architecture-unit>/<business-capability>.md`，一维设计使用 `<module-name>.md`。
- `<module-name>` 使用模块名生成稳定文件名：英文优先小写 kebab-case；中文模块名可以使用简洁中文，或转成稳定拼音 / 英文短名；同一工作区内不得重名。
- `progress.md` 用于管理总体模块进度，每个模块一条 checklist。
- 每个模块文件用 checklist 管理模块内子任务进度。
- 如果更新已有任务文件，尽量保留已经完成的 `[x]` 状态；除非用户明确要求重置。

## 模块任务文件模板

每个模块输出一个文件：

````markdown
# [模块名] 任务

## 模块来源

- 设计章节：[design.md 中的章节名]
- 架构归属：[design.md 中的架构单元；一维退化时写“单轴”]
- 业务归属：[design.md 中的业务能力]
- 业务映射：[优先对应 design.md 中的需求映射；如存在 plan.md，可补充对应流程 / 逻辑 / 验收点]
- 模块职责：[一句话说明模块负责什么]

## 执行顺序

- 前置依赖：[根据接口生产消费、数据所有权、运行前置条件推导；没有则写“无”]
- 依赖依据：[说明依赖来自哪条 design 契约；不要使用固定前后端顺序]

## 子任务清单

- [ ] [任务 1：最小可执行动作]
  - 输入：[需要读取的文件、接口、字段、状态或设计约束]
  - 输出：[完成后新增或改变什么]
  - 完成标准：[如何判断该任务完成]
  - 验证方式：[单测、集成测试、人工检查、类型检查、lint 等]
- [ ] [任务 2：最小可执行动作]
  - 输入：
  - 输出：
  - 完成标准：
  - 验证方式：

## 模块验收

- [ ] [来自 design.md 的模块级验收或独立测试要求]
- [ ] [如存在 plan.md，补充来自 plan.md 的相关业务验收点]

## 备注

- [实现时需要注意的依赖、边界、风险；没有则写“暂无”]
````

## 总体进度文件模板

`progress.md` 必须使用以下结构：

````markdown
# 任务进度

## 工作区

- 当前工作区：`./docs/[当前工作区]/`
- 输入计划：`./docs/[当前工作区]/plan.md`（如存在）
- 输入设计：`./docs/[当前工作区]/design.md`

## 任务进度

- [ ] [[架构归属] 业务任务 A](./架构单元/业务任务-a.md) - [一句话说明完成标准]
- [ ] [[架构归属] 业务任务 B](./架构单元/业务任务-b.md) - [一句话说明完成标准]

## 依赖图

- [生产者任务] -> [消费者任务]：[接口、状态、数据或运行前置依据]
- 可并行：[互不依赖且写入边界不冲突的任务]

## 全体验收

- [ ] 所有模块任务文件中的子任务均已完成。
- [ ] 所有模块验收 checklist 均已完成。
- [ ] 如果存在 `plan.md`，其中相关验收点已被模块任务覆盖。
- [ ] `design.md` 中每个具体模块的职责都已被任务覆盖。
- [ ] 每个任务的架构归属、业务归属和依赖依据都明确。
````

## 输出前自检

保存前必须检查：

1. 已确认当前工作区，且没有使用工作区外路径。
2. 已读取已有工作区中的 `design.md`；如果 `plan.md` 存在，也已作为背景输入读取。
3. `design.md` 中每个具体模块的职责都被任务文件完整覆盖；没有因二维拆分遗漏任一矩阵单元。
4. 每个模块任务文件都有 checklist 子任务和模块验收。
5. `progress.md` 中每个模块都有一条总体 checklist。
6. 任务足够小，适合 vibe coding 逐项执行。
7. 没有输出工时、排期、负责人或阶段式项目计划。
8. 没有用 `TBD`、`TODO`、`待补充` 占位。
9. 每个任务都有明确架构归属和业务归属；一维退化任务已标明依据。
10. `progress.md` 的依赖图来自 design 契约，没有套用固定端或固定层的执行顺序。

## 交付话术

完成后使用简短回复：

```markdown
已生成 `to-task` 任务文档并保存到 `./docs/[当前工作区]/tasks/`。

核心内容：
- 总体进度：`./docs/[当前工作区]/tasks/progress.md`
- 模块任务：[列出主要模块任务文件]
- 输入来源：`design.md`，以及可选背景 `plan.md`
```
